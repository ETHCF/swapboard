# Style Guide

Coding conventions for Swapboard. Project-specific rules take precedence over external guides.

Conventions below come from the [Solidity Style Guide](https://docs.soliditylang.org/en/latest/style-guide.html) plus decisions made specifically for this project.

## Solidity

Follow the Solidity Style Guide unless this document says otherwise.

Enforce formatting with Foundry (`make fmt`) and lint with `make lint` (`forge lint` + solhint). Config lives in `contracts/foundry.toml` and `contracts/.solhint.json`.

### Tooling defaults

| Setting | Value | Notes |
| --- | --- | --- |
| Compiler | `0.8.36` (pinned in `foundry.toml`) | Interfaces use `^0.8.0` |
| Indentation | 4 spaces | Matches the Solidity guide |
| Line length | **120** | Matches the Solidity guide |
| Quotes | Double | `forge fmt` |
| Integers | Explicit width (`uint256`, …) | `int_types = "long"` |
| Multiline headers | Params first | `multiline_func_header = "params_first"` |

### Naming

| Kind | Convention | Examples |
| --- | --- | --- |
| Contracts, libraries, interfaces, structs, events, enums, errors | CapWords | `Swapboard`, `Order`, `OrderCreated`, `ZeroAddress` |
| Functions, modifiers, arguments, locals | mixedCase | `createOrder`, `tokenA`, `amountB` |
| Private / internal state and helpers | leading `_` + mixedCase | `_nextOrderId`, `_orders`, `_pullExactToken` |
| Immutable / constant state | leading `_` + `UPPER_CASE` | `_ETH`, `_MAJOR` |
| Explicit getters | `get` + CapWords | `getEth`, `getNextOrderId`, `getOrder` |
| File names | Match the primary type | `Swapboard.sol`, `ISwapboard.sol` |

**Parameters** never use a leading or trailing underscore. Always `xxx` (e.g. constructor `major`, not `_major`). Prefer distinct names over collision hacks.

**`getXxx` exceptions:** use `get` for state/config accessors. Boolean/status helpers and established names may omit the prefix (`canFill`, `version`). Do not invent parallel names like `getCanFill`.

### Visibility and getters

- **Do not use `public` state variables.** Prefer `private` (or `internal` only when subclasses must read them). Autogenerated getters increase bytecode size and freeze an ABI shape you may not want.
- **Do not add a getter for every private field.** Expose state only when external callers need it.
- When a getter is needed, declare it explicitly (`external view`) and name it `getXxx` rather than mirroring the storage name (e.g. `_ETH` → `getEth()`, `_nextOrderId` → `getNextOrderId()`).
- Prefer a single structured getter over a redundant tuple getter that duplicates it (e.g. keep `getOrder`, do not also ship an `orders(uint256)` tuple getter).
- ERC20-style token APIs on mocks may keep the standard names (`name`, `symbol`, `balanceOf`, …) because those *are* the public token interface.
- Document getters that are part of the production ABI in `ISwapboard` (or the relevant interface) and cover them in tests.

### Named construction (`{key: value}`)

Always use **named** fields for struct literals and event emits. Never rely on positional arguments for structs or events — field reordering must not silently change meaning.

```solidity
_orders[orderId] = Order({
    maker: msg.sender,
    active: true,
    partialFillAllowed: partialFillAllowed,
    tokenA: tokenA,
    tokenB: tokenB,
    amountA: amountA,
    amountB: amountB,
    availableA: amountA,
    availableB: amountB
});

emit OrderCreated({
    orderId: orderId,
    maker: msg.sender,
    tokenA: tokenA,
    amountA: amountA,
    tokenB: tokenB,
    amountB: amountB,
    partialFillAllowed: partialFillAllowed
});

emit OrderFilled({orderId: orderId, taker: msg.sender, amountA: amountA, amountB: amountBIn});
```

Prefer the same style for any other named-argument call sites where Solidity supports them (e.g. nested struct construction).

### Errors and events

- Use **custom errors** (`error ZeroAddress();` / `revert ZeroAddress();`), not `require`/`revert` with string reasons.
- Declare **structs, events, and errors on the project interface**; implementing contracts inherit them and do not redeclare the ABI surface.
- Collapse checks that revert with the **same error** into one `if` when the error payload is identical:

```solidity
if (tokenA == address(0) || tokenB == address(0)) {
    revert ZeroAddress();
}
```

Keep separate `if`s when the error encodes different data (e.g. `NotAContract(tokenA)` vs `NotAContract(tokenB)`).

- Scope solhint disables tightly around intentional ABI choices (e.g. non-indexed fields on `OrderCreated`), and re-enable immediately after.

### Storage reads and returns

- **Snapshot storage structs into locals** (tuple unpack) before a sequence of checks/transfers when multiple fields are read:

```solidity
(address maker, bool active, address tokenA, address tokenB, uint128 amountA, uint128 amountB) =
    (order.maker, order.active, order.tokenA, order.tokenB, order.amountA, order.amountB);
```

- Use **named mapping keys**: `mapping(uint256 orderId => Order order)`.
- Prefer **named returns only when necessary**: the return value is assigned mid-function and returned implicitly (no clean single terminal `return`), e.g. `createOrder` → `returns (uint256 orderId)`. Prefer an unnamed type plus an explicit `return` when a local + `return` is equally clear (`getOrder`, `getOrders`).
- External array arguments use **`calldata`** unless the function must mutate the array in place.
- Prefer **prefix increments** (`++i`, `++_nextOrderId`) inside `unchecked` counter/loop blocks.

### Checks-Effects-Interactions and `unchecked`

- For paths that move value (ETH or ERC20), follow **Checks → Effects → Interactions**: validate, then write effects (e.g. `order.active = false`), then transfer/`sendValue`, then emit.
- Exception: escrow **pulls on create** may run before recording the order so a failed pull never leaves a live order.
- Document that ETH outflows use `Address.sendValue` (forwards gas) and always run after effects.
- Use **`unchecked` only with an adjacent justification** (comment or obvious impossibility of overflow): monotonic counters, loop indices bounded by `array.length`, and post-transfer balance deltas.

### Exact ETH accounting

Payable entrypoints that optionally take ETH must enforce **exact `msg.value`**, including `requiredEth == 0` when the path is ERC20-only:

```solidity
uint256 requiredEth = tokenB == _ETH ? amountB : 0;
if (msg.value != requiredEth) {
    revert ETHAmountMismatch(requiredEth, msg.value);
}
```

### Imports and inheritance

- Use **named imports**: `import {Swapboard} from "./Swapboard.sol";` (never bare `import "./X.sol";`).
- Attach libraries with `using Lib for Type` at the top of the contract body.
- Inheritance order: project interface(s) → project bases → external bases (e.g. `ISwapboard, Semver, ReentrancyGuardTransient`).

### Layout

**One primary contract / interface / library per file.** Project interfaces live under `contracts/src/interfaces/`. Thin vendor interfaces (if any) under `contracts/src/vendor/`.

**File order:** SPDX → pragma → imports → contract/interface.

**Inside a contract / interface:**

1. Type declarations (structs, enums)
2. State variables
3. Events
4. Errors
5. Modifiers
6. Functions

**Function order** (Solidity guide):

1. `constructor`
2. `receive` (if any)
3. `fallback` (if any)
4. External (non-`view` / non-`pure`)
5. Public
6. Internal
7. Private

Within each visibility group, put `view` and `pure` last. Private helpers that exist only to support mutators belong after the public/external surface.

Modifier order on a function: visibility → mutability → `virtual` → `override` → custom modifiers (e.g. `nonReentrant`).

### Formatting differences from the Solidity guide

These are intentional project choices (mostly via `forge fmt`):

1. **Long function headers** keep visibility/modifiers/`returns` on the same line as the closing `)` of the parameter list (`params_first`), instead of putting each modifier on its own line under `)`.
2. **Immutables / constants** use `_UPPER_CASE` (guide treats plain state as mixedCase and only constants as `UPPER_CASE`).
3. Put a **blank line between unrelated steps** in a function body (e.g. validate → pull → assign id → store → emit). Keep tightly related CEI pairs grouped (effect immediately above its interaction) without forcing a blank line between `active = false` and the first transfer.
4. Prefer **named `{key: value}`** construction for structs and events even when `forge fmt` packs short emits onto one line.

### NatSpec

- Annotate the public ABI (interface + implementing contract) with NatSpec.
- Use `///` (or `/** */`) directly above the declaration.
- Prefer `@inheritdoc` on implementations when the interface already documents the function.
- Add `@dev` for non-obvious security or accounting behavior.
- Private helpers may use `@notice`/`@param` when useful for reviewers; prefer `@dev` when the helper is purely internal mechanics.
- Keep `@param` order on structs aligned with the field declaration order.

### Interfaces, pragmas, and coverage

- `contracts/src/interfaces/` and thin vendor interfaces may use `pragma solidity ^0.8.0`.
- Implementation, scripts, and tests pin an exact compiler version via `pragma solidity 0.8.36` and `foundry.toml`.
- Coverage excludes `test/` (`no_match_coverage` / `make coverage`); do not rely on mock/handler-only getters for production coverage numbers.
- Do not modify `contracts/src/legacy/**` for style cleanups unless the change is explicitly about legacy compatibility.
