# Style Guide

Coding conventions for Swapboard. Project-specific rules take precedence over external guides.

Conventions below come from the [Solidity Style Guide](https://docs.soliditylang.org/en/latest/style-guide.html) plus decisions made on the `v2` / follow-up refactoring work.

## Solidity

Follow the Solidity Style Guide unless this document says otherwise.

Enforce formatting with Foundry (`make fmt`) and lint with `make lint` (`forge lint` + solhint). Config lives in `contracts/foundry.toml` and `contracts/.solhint.json`.

### Tooling defaults

| Setting | Value | Notes |
| --- | --- | --- |
| Compiler | `0.8.36` (pinned in `foundry.toml`) | Interfaces use `^0.8.0` |
| Indentation | 4 spaces | Matches the Solidity guide |
| Line length | **120** | Matches the Solidity guide |
| Quotes | Double | `forge fmt` |
| Integers | Explicit width (`uint256`, …) | `int_types = "long"` |
| Multiline headers | Params first | `multiline_func_header = "params_first"` |

### Naming

| Kind | Convention | Examples |
| --- | --- | --- |
| Contracts, libraries, interfaces, structs, events, enums, errors | CapWords | `Swapboard`, `Order`, `OrderCreated`, `ZeroAddress` |
| Functions, modifiers, arguments, locals | mixedCase | `createOrder`, `tokenA`, `amountB` |
| Private / internal state and helpers | leading `_` + mixedCase | `_nextOrderId`, `_orders`, `_mint` |
| Immutable / constant-like state | leading `_` + `UPPER_CASE` | `_WETH`, `_BOARD` |
| Explicit getters | `get` + CapWords | `getWeth`, `getNextOrderId`, `getOrder` |
| File names | Match the primary type | `Swapboard.sol`, `ISwapboard.sol` |

**Parameters** never use a leading or trailing underscore. Always `xxx` (e.g. constructor `weth`, not `_weth` or `weth_`). Prefer distinct names over collision hacks; sharing a name with a getter in a constructor is acceptable.

### Visibility and getters

- **Do not use `public` state variables.** Prefer `private` (or `internal` only when subclasses must read them). Autogenerated getters increase bytecode size and freeze an ABI shape you may not want.
- **Do not add a getter for every private field.** Expose state only when external callers (users, integrators, tests of production API, or the interface) need it.
- When a getter is needed, declare it explicitly (`external view`) and name it `getXxx` rather than mirroring the storage name (e.g. `_WETH` → `getWeth()`, `_nextOrderId` → `getNextOrderId()`).
- Prefer a single structured getter over a redundant tuple getter that duplicates it (e.g. keep `getOrder`, do not also ship an `orders(uint256)` tuple getter).
- ERC20-style token APIs on mocks may keep the standard names (`name`, `symbol`, `balanceOf`, …) because those *are* the public token interface.
- Document getters that are part of the production ABI in `ISwapboard` (or the relevant interface) and cover them in tests. Skip getters that exist only on test mocks/handlers unless they are under test themselves.

### Errors and events

- Use **custom errors** (`error ZeroAddress();` / `revert ZeroAddress();`), not `require`/`revert` with string reasons.
- Prefer **named** struct construction and event emits:

```solidity
_orders[orderId] = Order({
    maker: msg.sender,
    active: true,
    tokenA: tokenA,
    amountA: amountA,
    tokenB: tokenB,
    amountB: amountB
});

emit OrderFilled({orderId: orderId, taker: msg.sender});
```

### Layout

**One primary contract / interface / library per file.** Thin vendor interfaces live under `contracts/src/vendor/` (e.g. `IWETH.sol`); project interfaces under `contracts/src/interfaces/`.

**File order:** SPDX → pragma → imports → contract/interface.

**Inside a contract / interface:**

1. Type declarations (structs, enums)
2. State variables
3. Events
4. Errors
5. Modifiers
6. Functions

**Function order** (Solidity guide):

1. `constructor`
2. `receive` (if any)
3. `fallback` (if any)
4. External (non-`view` / non-`pure`)
5. Public
6. Internal
7. Private

Within each visibility group, put `view` and `pure` last.

Modifier order on a function: visibility → mutability → `virtual` → `override` → custom modifiers (e.g. `nonReentrant`).

### Formatting differences from the Solidity guide

These are intentional project choices (mostly via `forge fmt`):

1. **Long function headers** keep visibility/modifiers/`returns` on the same line as the closing `)` of the parameter list (`params_first`), instead of putting each modifier on its own line under `)`.
2. **Immutables** use `_UPPER_CASE` (guide treats plain state as mixedCase and only constants as `UPPER_CASE`).
3. Put a **blank line between unrelated steps** in a function body (e.g. state update → emit → return). Keep tightly related statements grouped (e.g. paired balance reads around a transfer).
4. Collapse checks that revert with the **same error** into one `if` when the error payload is identical:

```solidity
if (tokenA == address(0) || tokenB == address(0)) {
    revert ZeroAddress();
}
```

Keep separate `if`s when the error encodes different data (e.g. `NotAContract(tokenA)` vs `NotAContract(tokenB)`).

### NatSpec

- Annotate the public ABI (interface + implementing contract) with NatSpec.
- Use `///` (or `/** */`) directly above the declaration.
- Prefer `@inheritdoc` on implementations when the interface already documents the function.
- Add `@dev` for non-obvious security or accounting behavior.

### Interfaces, pragmas, and coverage

- `contracts/src/interfaces/` and thin vendor interfaces may use `pragma solidity ^0.8.0`.
- Implementation, scripts, and tests pin an exact compiler version via `pragma solidity 0.8.36` and `foundry.toml`.
- Coverage excludes `test/` (`no_match_coverage` / `make coverage`); do not rely on mock/handler-only getters for production coverage numbers.
